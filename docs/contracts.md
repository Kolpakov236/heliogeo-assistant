# Контракты

Контракты — доменные данные, которые должен править и подписывать предметный эксперт
(гелиогеофизик), а не программист: реестр фактов, словарь терминов (лексикон), пороги, каталог
разрывов данных, спецификации признаков. Принцип: предметные пороги и словари не хранятся в коде.
Если для правки порога нужен релиз, порог не будет меняться никогда, и система разойдётся с
действительностью.

Контракты лежат в `contracts/` (корень репозитория, вне `src/`) и отличаются от `configs/`
(технические настройки: промпты, логирование) версиями и подписью. Код читает и проверяет их через
пакет `heliogeo.contracts`.

## Состав

| Файл | Вид | Содержимое | Состояние |
|---|---|---|---|
| `contracts/facts/registry.yaml` | `facts` | реестр фактов: величины, из которых строятся тексты (id, тип, единицы, источник, правила качества, шаблоны формулировок) | заготовка, пока пусто |
| `contracts/lexicon/terms.yaml` | `lexicon` | словарь терминов и списки запрещённых формулировок | заготовка, пока пусто |
| `contracts/rules/thresholds.yaml` | `thresholds` | пороги и шкалы: словесная шкала бурь, шкала «вероятность → слово» и т. п. | заготовка, пока пусто |
| `contracts/homogenization/discontinuities.yaml` | `homogenization` | разрывы в рядах данных (смена спутника, пересчёт шкалы) и коэффициенты приведения к единой шкале | заготовка, пока пусто |
| `contracts/features/specs.yaml` | `features` | спецификации признаков для моделей прогноза с задержками доступности | заполнен, 40 признаков |
| `contracts/versions.lock.json` | — | версии и хэши контрактов | генерируется (`make contracts-lock`) |

Каталог по умолчанию — `contracts/` в корне репозитория; его можно переопределить переменной
окружения `CONTRACTS_DIR` (относительный путь считается от корня репозитория).

## Конверт

Каждый контракт начинается с одних и тех же трёх полей:

```yaml
version: "0.1.0"        # строка X.Y.Z: подходит и 0.1.0, и календарная 2026.10.1
approved_by: null       # имя эксперта; null — черновик
approved_at: null       # дата подписи (ГГГГ-ММ-ДД); null — черновик
```

- Версия — строка в кавычках: без них YAML читает `1.0` как число, и такой файл отклоняется.
- `approved_by` и `approved_at` присутствуют всегда и заполняются вместе (или обе `null`).
  Заглушки вместо имени (`<эксперт>`, `...`, `TODO`) и дата в будущем отклоняются.
- Неподписанный контракт допустим при разработке (предупреждение), для релиза проверка запускается
  с `--strict` и требует подписи у каждого контракта.

## Версии и lock-файл

Содержимое контракта нельзя изменить, не повысив `version`. Это обеспечивает `versions.lock.json`:
для каждого файла в нём записаны версия и SHA-256 «тела» контракта.

Порядок работы:

1. Изменили контракт — повысили `version` (правка без повышения не пройдёт проверку).
2. Выполнили `make contracts-lock`: lock-файл обновится, а если версия не выросла, команда
   откажется писать и назовёт файл.
3. Закоммитили контракт и `versions.lock.json` вместе.

Что считается изменением. Хэш считается по разобранным данным, а не по тексту: комментарии, порядок
ключей, кавычки и окончания строк (CRLF/LF) на него не влияют. Подпись эксперта (`approved_by`,
`approved_at`) в хэш не входит, поэтому подписать уже слитую версию можно без её повышения.

Как повышать версию (рекомендация): правка формулировок и заметок — третье число, новые записи —
второе, переименование или удаление `id` и смысловые изменения — первое.

| Сообщение валидатора | Что делать |
|---|---|
| `содержимое изменено, а version не повышена` | поднять `version`, затем `make contracts-lock` |
| `versions.lock.json устарел (version A -> B)` | выполнить `make contracts-lock` |
| `version понижена` | вернуть версию не ниже записанной в lock-файле |
| `нет в versions.lock.json` / `нет versions.lock.json` | выполнить `make contracts-lock` |

## Проверка

```
make contracts                                    # то же, что python -m heliogeo.contracts.validate
python -m heliogeo.contracts.validate --strict    # требовать подписи экспертом (для релиза)
python -m heliogeo.contracts.validate --dir PATH  # другой каталог контрактов
```

`make lint` тоже запускает проверку. Код возврата: 0 — ошибок нет, 1 — есть ошибки. Проверяется:

- каждый `*.yaml` каталога зарегистрирован в `heliogeo/contracts/kinds.py`, каждый
  зарегистрированный файл существует;
- YAML читается безопасно, ключи не повторяются (PyYAML молча берёт последний дубль);
- конверт и тело проходят модель своего вида;
- `id` внутри файла уникальны;
- содержимое согласовано с `versions.lock.json`;
- проходят проверки ссылок между контрактами (`kinds.CROSS_CHECKS`; пока их нет: они понадобятся,
  когда реестр фактов начнёт ссылаться на словарь терминов).

CI пока не подключён: когда он появится, достаточно вызвать `make lint` или
`python -m heliogeo.contracts.validate`. Проверка репозитория также входит в `make test`
(`tests/unit/test_contracts_repo.py`).

## Как добавить контракт

1. Создать YAML с конвертом в `contracts/<каталог>/`.
2. Зарегистрировать вид в `KINDS` (`heliogeo/contracts/kinds.py`): имя, путь, модель. Для файла, тело
   которого ещё не специфицировано, подходит `DraftContract` (проверяется только конверт); строгую
   модель тела задаёт тот, кто наполняет файл.
3. `make contracts-lock`, затем `make contracts`.
4. Тесты: фабрики временных контрактов лежат в `tests/mocks/contracts.py`.

## Спецификации признаков (`features/specs.yaml`)

Признак — входная величина модели прогноза, посчитанная из наблюдений (например, максимум индекса
Kp за сутки). Чтобы модель не использовала то, что на момент прогноза ещё не было известно («утечка
будущего»), у каждого признака объявлена задержка доступности `available_delay`: признак на момент
`t` считается только по данным с меткой времени не позже `t - available_delay`. Окна «за N суток»
заканчиваются в этот же момент. Модуль, который будет собирать строки признаков по этим
спецификациям (Feature Store), пока не написан: файл описывает, какие признаки и с какими
задержками он должен считать.

```yaml
features:
  - id: kp_max_1d
    group: activity_history
    description: "Максимум трёхчасового Kp за 24 часа, оканчивающихся в t - available_delay"
    available_delay: PT3H
    status: planned
    note: "предварительно: трёхчасовые интервалы + публикация"
```

| Поле | Правило |
|---|---|
| `id` | `snake_case`, уникален в файле |
| `group` | одна из семи групп (см. ниже) |
| `description` | на русском, непусто |
| `available_delay` | обязателен, без значения по умолчанию; ISO 8601 только в днях и времени (`PT3H` — 3 часа, `P1D` — сутки, `PT0S` — без задержки, `PT1H30M`); неотрицательный; месяцы, годы и недели не допускаются |
| `status` | `planned` — объявлен, но модуль признаков его ещё не считает; `active` — считает |
| `note` | необязательно: обоснование задержки |

Версия файла — это `feature_set_v`, версия набора признаков. Она записывается в
`forecast.feature_set_v` (а позже и в строки признаков), и любое изменение состава, задержек или
статусов повышает её. Поэтому строка признаков вместе с версией однозначно определяет, какие
признаки в неё вошли.

Группы и состав (40 признаков, все `planned`):

| Группа | Признаки | Задержка |
|---|---|---|
| `activity_history` | `kp_cur`, `kp_max_1d/3d/7d`, `kp_mean_1d/3d/7d`, `kp_trend_3d`, `dst_min_1d` | PT3H |
| `recurrence` | `kp_recurrence_27d`, `kp_recurrence_54d` | PT3H |
| `solar_wind` | `sw_speed_min/avg/max`, `sw_density_avg`, `sw_bt`, `sw_bz_min`, `sw_sector`, `sw_speed_trend_24h` | PT1H |
| `solar_activity` | `ar_count`, `ar_total_area`, `ar_has_delta`, `ar_max_mcintosh_z`, `ar_new_count`, `flares_c/m/x_24h`, `flare_max_flux_24h`, `days_since_last_m/x` | PT1H |
| `cme` | `cme_count_24h`, `cme_earth_directed`, `cme_direction_unknown`, `cme_speed_max_24h`, `cme_width_max_24h`, `cme_earth_directed_speed_max_24h` | P1D |
| `calendar` | `doy`, `cycle_proxy` | PT0S, PT1H |
| `external_forecast` | `swpc_g_scale`, `swpc_r_scale` | PT0S |

Термины:
- **Kp** — трёхчасовой индекс геомагнитной активности (шкала 0–9), **Dst** — индекс геомагнитных
  бурь (нТл);
- `recurrence` — значения Kp 27 и 54 суток назад (период вращения Солнца 27,2753 суток: потоки из
  корональных дыр повторяются);
- `solar_wind` — измерения солнечного ветра в точке L1 между Землёй и Солнцем, примерно за час до
  прихода ветра к Земле; Bt и Bz — величина и северо-южная компонента межпланетного магнитного
  поля; `sw_sector` — направление поля (`toward` или `away`);
- `solar_activity` — активные области (`ar_*`, классификация групп пятен McIntosh) и вспышки
  (`flares_*`, классы C, M, X);
- `cme` — корональные выбросы массы, `cme_earth_directed` — направленные к Земле;
- `cycle_proxy` — косвенная оценка фазы солнечного цикла;
- `external_forecast` — шкалы G (геомагнитные бури) и R (радиопомехи) из прогноза Центра
  прогнозирования космической погоды NOAA (SWPC).

Предполагаются две версии модели: автономная (все группы, кроме `external_forecast`) и расширенная
(все группы). Разница их качества показывает, сколько модель добавляет к прогнозу SWPC; автономная
работает и тогда, когда чужого прогноза нет.

Задержки предварительные. Они подобраны консервативно по характеру источников: трёхчасовые
интервалы Kp плюс публикация (PT3H), измерения ветра почти в реальном времени (PT1H), каталог
выбросов отстаёт (P1D), прогноз SWPC приходит вместе с выпуском (PT0S), для активных областей и
вспышек взят запас в час. Файл не подписан, у каждой задержки есть пометка «предварительно» в
`note`: подтвердить их должен владелец SWX API или предметный эксперт.

Сознательно не включено (нужны данные или модели, которых нет):
- производные ветра (энергия связки «скорость — поле», длительность отрицательного Bz): нужны ряды
  измерений, а не суточные агрегаты;
- время прихода выброса: нужна модель его торможения;
- счётчики областей по классам McIntosh и магнитным классам: понадобятся модели вспышек;
- относительные варианты признаков (перцентильный ранг, отношение к медиане): устойчивы к смене
  приборов;
- признаки прибора (идентификатор спутника или ряда данных).

Каждая такая добавка поднимает версию набора.

Чтение из кода:

```python
from heliogeo.contracts.features import load_feature_specs

specs = load_feature_specs()        # проверяет файл; ContractError, если он некорректен
specs.version                       # feature_set_v
for spec in specs.active():         # признаки со статусом active
    cutoff = t - spec.available_delay    # available_delay — timedelta
```

Колонки таблицы `observation_daily`, из которых считаются признаки, — в
[database.md](database.md).
