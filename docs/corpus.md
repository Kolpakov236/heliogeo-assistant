# Корпус эталонных текстов и архив данных

Зачем: для эталонной генерации нужны (1) тексты, которые реально пишут специалисты NOAA, и
(2) данные, к которым эти тексты относятся. Бэкфилл складывает и то и другое в локальное хранилище,
из текстов собирается индекс, по которому их быстро достают.

## Быстрый старт

```bash
# скачать год (повторный запуск безопасен: цело лежащее в хранилище в сеть не ходит)
poetry run heliogeo corpus backfill --from 2025-10-28 --to 2026-10-27

poetry run heliogeo corpus stats --missing          # сколько выпусков, период, пропуски
poetry run heliogeo corpus show 2026-01-15T00:30    # один выпуск: разделы и сутки данных для пары
poetry run heliogeo corpus search "M-class" --kind discussion --limit 5
poetry run heliogeo corpus build                    # пересобрать индекс из сырого слоя, без сети
```

Период задаётся явно (системные часы код не читает) и должен заканчиваться **не позже, чем за двое
суток до «сейчас»**: ближе к сегодняшнему дню источник подмешивает live-данные, и ответ уже не
воспроизводится. Запросы идут с `no_live`, но свежие сутки всё равно могут быть неполными.

Параметры: `--delay` (пауза между запросами, по умолчанию 0,4 с), `--max-failures` (остановка после
стольких подряд ошибок «источник недоступен», по умолчанию 5), `--no-normalize`, `--no-build`.
Остановленный бэкфилл не теряет сделанного: запустите ту же команду позже.

## Что скачивается за сутки

Четыре запроса, всё без live:

| Запрос | Что приходит | Кто делает |
|---|---|---|
| `/data` на 23:59 | снимок суток (области, вспышки, выбросы, ветер, Kp, Dst, частицы) | `fn-ingest` |
| `/text` на 23:59 | RSGA 22:00 (последний выпуск суток) | `fn-ingest` |
| `/text` на 00:30 | Forecast Discussion 00:30 | бэкфилл |
| `/text` на 12:30 | Forecast Discussion 12:30 | бэкфилл |

Ingest спрашивает только на 23:59, а на этот момент Discussion уже не «последний выпуск», хотя он
есть в `available`. Поэтому два Discussion докачиваются отдельно. Итого **три выпуска в сутки**:
Discussion 00:30 и 12:30 (разделы `Solar Activity`, `Energetic Particle`, `Solar Wind`, `Geospace`,
у каждого `24 hr Summary` и `Forecast`) и RSGA 22:00 (разделы `solar_analysis`, `solar_forecast`,
`geophysical_summary`, `geophysical_forecast`, `event_probabilities`, `f107`, `a_indices`,
`geomagnetic_probabilities` плюс вероятности и индексы). RSGA ценен для прогноза: в нём вероятности
вспышек и геомагнитных возмущений на три суток.

После скачивания `fn-normalize` строит из `/data` семь Parquet-разделов L1 (набор данных), а
индекс собирает тексты (корпус).

## Где лежит

Хранилище локальное (`OBJECT_STORE=local`, каталог `OBJECT_STORE_DIR`, по умолчанию `var/objects`,
он в `.gitignore`); раскладка повторяет облачную:

```
var/objects/heliogeo-raw/_manifest/2026-01-15.json                       что скачано за дату (хэши, моменты)
var/objects/heliogeo-raw/live/2026-01-15/2359/data_ut_day_nolive.json    тело /data как пришло
var/objects/heliogeo-raw/live/2026-01-15/{0030,1230,2359}/text_nolive.json   тела /text
var/objects/heliogeo-lake/l1/{сущность}/dt=2026-01-15/part-000.parquet   нормализованные данные
var/objects/heliogeo-lake/corpus/texts_v1.jsonl                          индекс текстов
```

Тела хранятся байтами как получены, до разбора: если парсер окажется с ошибкой, всё пересоберётся
без повторного обращения к источнику.

## Работа с корпусом из кода

```python
from datetime import date

from heliogeo.corpus import Corpus
from heliogeo.storage.factory import open_object_store
from heliogeo.storage.keys import Bucket

corpus = Corpus.load(open_object_store(Bucket.LAKE))   # один объект читается за доли секунды

corpus.select(kind="discussion", cycle="0030", start=date(2026, 1, 1), end=date(2026, 3, 31))
for record, text in corpus.sections("Solar Activity", part="24 hr Summary"):
    ...                                                 # разделы по всем выпускам
for record, line in corpus.search(r"M-class", kind="discussion"):
    ...                                                 # строки по регулярному выражению
corpus.sentences(record, "Geospace", "Forecast")        # предложения раздела
corpus.missing_issues()                                 # дыры относительно расписания источника
```

Запись `TextRecord`: `issued_utc`, `kind`, `cycle`, `sections` (`{раздел: {часть: текст}}`),
`text`, `probabilities`/`a_indices`/`f107` (RSGA), `raw_key`, `raw_sha256` (откуда взято).

## Выравнивание окон: главная ловушка

Текст описывает **24 часа, оканчивающиеся в момент выпуска**. Discussion 00:30 за 15 января говорит о
сутках 14 января, а не о 15-м. Склеивать `/data/{D}` с `/text/{D}` напрямую нельзя: пересечение
окон — полчаса, и все метрики «текст соответствует данным» окажутся систематически плохими.
Поэтому у записи есть `covers_from`/`covers_to` и `data_days`: сутки данных, которые нужны для пары
(обычно два: накануне и день выпуска). Для RSGA 22:00 это такое же приближение. Дальше данные за
эти сутки берутся из L1 (`heliogeo.storage.lake.read_range`) и обрезаются по окну.

## Ограничения

- **Текущий парсер `SwxTextResponse` теряет разделы RSGA.** Он понимает только разделы-словари
  (Discussion), а у RSGA разделы — строки: `sections` остаётся пустым, а в журнале на каждый ответ
  8 предупреждений «is not an object». Сырое тело и полный `text` при этом сохраняются, поэтому
  корпус читает разделы из сырого тела. Сам парсер не менялся (на нём завязаны его тесты); если
  понадобится структурный разбор RSGA в клиенте, это отдельная задача.
- **Расписание выпусков** — наблюдаемое на сегодня (Discussion 00:30 и 12:30, RSGA 22:00):
  `EXPECTED_ISSUES` в `corpus/index.py`. Для более ранних лет оно может быть другим (по документации
  источника, до 1 марта 2024 вместо Discussion выходил только RSGA); тогда `missing_issues` покажет
  «пропуски», которые на деле особенности архива.
- **Эталон содержит ошибки** (например, «solar wind speeds … to ~4 km/s» вместо ~400): корпус
  хранит тексты как есть, а выбор и чистка — задача того, кто строит из них эталонный набор.
- Пустые сутки в архиве источника (404 на `/data`) не прерывают бэкфилл: они попадают в отчёт как
  ошибка `DATA_INSUFFICIENT`.
