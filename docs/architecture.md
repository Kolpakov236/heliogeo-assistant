# Архитектура Heliogeo Assistant

## Назначение

Автоматизированная система помощи гелиогеофизику. Замещает ручную подготовку:
- ICAO HANDOVER BRIEF (авиация)
- SWPC Forecast Discussion (NOAA)
- Упрощённых версий для пилотов, радиолюбителей

Работает по расписанию и по запросу: один запуск — один выпуск.

## Ключевой принцип

**Один Unified JSON → несколько продуктов.** LLM получает только данные из JSON, grounding-проверка исключает галлюцинации.

Направление развития — слот-референсная генерация: модель не пишет чисел вообще, а возвращает
последовательность сегментов, где свободный текст не содержит цифр, а все числа и термины —
ссылки на идентификаторы фактов (`heliogeo.facts`). Числовая галлюцинация тогда невозможна
структурно, а не просто маловероятна; проверка grounding остаётся второй линией.

## Облачный контур (Yandex Cloud, serverless)

Оркестрация — Yandex Workflows, вычисления — Cloud Functions, объёмные данные — Object Storage,
оперативное состояние — YDB, аналитика — Yandex Query по Parquet. Постоянно работающих серверов
нет: состояния между вызовами функций тоже нет, всё нужное лежит в хранилищах.

```
  расписание ──▶ WF-DAILY (Workflows): один запуск = один выпуск бюллетеня
                    │  шаги обмениваются КЛЮЧАМИ объектов, а не данными
  ingest → normalize → features → forecast → generate → validate → render-deliver
     │         │           │          │          │          │           │
     ▼         ▼           ▼          ▼          ▼          ▼           ▼
  ╔═══════════════════════════════════════════════════════════════════════════╗
  ║ Object Storage: raw (сырьё) · lake (Parquet) · artifacts (модели) · issues║
  ╚═══════════════════════════════════════════════════════════════════════════╝
     YDB — прогоны, выпуски, прогнозы, верификация, метрики, реестр версий
     Yandex Query — SQL по Parquet: обучающие выборки, метрики, ретроспектива

  раз в сутки ─▶ WF-VERIFY: верификация созревших прогнозов, метрики, перекалибровка
  вручную ─────▶ WF-BACKFILL: Foreach по месяцам, одна итерация — один вызов функции
```

### Хранилища

Правило разделения: **Object Storage** — всё, что пишется один раз и читается пачками; **YDB** —
всё, что меняется и читается по одной записи с низкой задержкой; **Yandex Query** ничего не хранит,
а читает Object Storage, когда нужен SQL по большому объёму. В пути выпуска бюллетеня Yandex Query
не используется: запрос по Parquet — секунды и дороже, генерация читает уже посчитанное из YDB.

| Бакет | Что лежит | Особенности |
|---|---|---|
| `{prefix}-raw` | `warehouse/{product}/{YYYY}/{filename}` — файлы NOAA как получены, с раскладкой каталогов источника; `live/{YYYY-MM-DD}/{HHMM}/{name}` — снимки live-эндпоинтов; `_manifest/{YYYY-MM-DD}.json` — что скачано: размеры, хэши, коды ответов | версионирование, блокировка объектов на 90 суток |
| `{prefix}-lake` | `l1/{entity}/dt={YYYY-MM-DD}/part-000.parquet` — нормализованные сущности; `l2/features`, `l2/targets`, `l2/forecasts` с той же разметкой — признаки (корректные на момент времени), цели, копия прогнозов для аналитики | Parquet; `dt=` — Hive-разделы, по ним читается срез по датам, а не весь архив; холодное хранение через 180 суток |
| `{prefix}-artifacts` | `models/{model}/{version}/model.json` и `card.md`, `calibrators/…`, `registry/current.json` — указатель на действующие версии, `lexicon/{version}.yaml`, `rules/{version}.yaml` | версионирование, удаление запрещено политикой |
| `{prefix}-issues` | `{YYYY-MM-DD}/{run_id}/payload.json`, `draft.json`, `bulletin.txt`, `trace.json` | версионирование |

Ключи объектов строятся только функциями-построителями, а не склеиваются руками: если один
напишет `dt=2026-10-05`, а другой `date=2026-10-05`, Yandex Query увидит две схемы разделов.
Раскладка сырья повторяет раскладку каталогов самого источника один в один, поэтому архив
синхронизируется в бакет как есть. Таблицы YDB и их отличия от локальной PostgreSQL —
в [database.md](database.md).

### Функции и воркфлоу

Квота облака — 10 функций; состав фиксирован девятью, десятая остаётся запасом. Часть работы
делают встроенные шаги воркфлоу (чтение и запись объектов, документные таблицы YDB, почта),
поэтому отдельных функций под неё нет.

| Функция | Что делает | Где в репозитории |
|---|---|---|
| `fn-ingest` | качает продукты за дату в `raw`, пишет манифест | `extractors/swx` (сейчас — клиент снимков), `mirror/` |
| `fn-normalize` | `raw` → `l1` (Parquet), парсеры источника | `extractors/swx/mapper.py`; перенос парсеров источника — впереди |
| `fn-features` | `l1` → `l2/features` и `l2/targets` с задержками доступности | `features/`, `contracts/features/specs.yaml` |
| `fn-forecast` | прогнозы всех источников и моделей, зависимость только numpy | `forecast/` |
| `fn-generate` | payload, запрос к модели, сегменты | `pipeline/builder.py`, `generation/`, `llm/`, `products/` |
| `fn-validate` | шлюзы проверки, вердикт | `validation/`, `llm/grounding.py` |
| `fn-render-deliver` | сборка текста, рендер, доставка | `render/`, `delivery/`, `publishing/` |
| `fn-verify` | верификация созревших прогнозов, метрики, перекалибровка | `eval/`, таблицы `forecast_verification` и `rolling_metrics` |
| `fn-admin` | кусок бэкфилла, пересборка витрин, служебное | — |

Генерация и проверка — разные функции, хотя обе обращаются к модели: их нужно уметь перезапускать
независимо. Отказ проверки не должен вести к повторной генерации: она стоит денег и даёт другой
текст, а проверять нужно ровно тот, что уже сгенерирован.

Спецификация суточного воркфлоу — `deploy/workflows/daily.yaml` (формат YaWL). Расписание
(cron и часовой пояс) задаётся на самом воркфлоу и запускает его без входных данных, поэтому
`run_id` и дату выпуска выдаёт первый шаг `open_run` — единственное место запуска, где читаются
системные часы. Ещё в спецификации три решения: ремонт текста ровно один раз; обязательная ветка `fallback` (если генерация или проверка не
удались, выпускается шаблонный текст из полей payload без участия модели: пропуск выпуска хуже
сухой формулировки); недоступность источника не срывает выпуск, а ведёт к выпуску с оговоркой о
неполноте данных. Воркфлоу верификации и бэкфилла пока не описаны.

### Правила, общие для всех функций

1. **Указатели вместо данных.** Вход функции — `{run_id, date, attempt, in: {ключи}, cfg}`, ответ —
   `{ok, out: {ключи}, metrics, notes}` или `{ok: false, error: {class, retryable, message,
   detail_key}}`. Ответ не больше 256 КБ (лимит платформы — 3,5 МБ, а шаг воркфлоу вмещает 2 МБ).
   Длинные диагностические тексты уходят в Object Storage, в ответе остаётся ключ.
2. **Время берётся из события, а не из системных часов.** Функция, читающая часы, невоспроизводима:
   на бэкфилле она подставила бы сегодняшний момент в 2019 год. Часы читают только точки входа, а
   остальной код получает момент параметром (момент запроса, `metadata.issued_utc` payload);
   список разрешённых мест держит тест `tests/unit/test_time_sources.py`.
3. **Повторный запуск за ту же дату перезаписывает, а не дублирует.** Ключи Object Storage и
   первичные ключи YDB детерминированы от `(date, kind, …)`; идентификатор прогноза — не случайный,
   а вида `2026-10-05/geomag_level/1/m0`. `run_id` — `{ISO-время запуска}/{kind}/{ULID}`.
4. **Закрытый перечень классов ошибок** (`ErrorClass` в `pipeline/pipeline.py`): по классу воркфлоу
   решает, повторять ли шаг.

   | Класс | Повторять | Пример |
   |---|---|---|
   | `SOURCE_UNAVAILABLE` | да | источник отдал 503 |
   | `TRANSIENT` | да | таймаут сети, троттлинг |
   | `LLM_TIMEOUT` | да | модель не ответила |
   | `SOURCE_MALFORMED` | нет | файл скачался, но не разбирается |
   | `LLM_INVALID_OUTPUT` | нет | ответ модели не прошёл схему: нужен ремонт, а не повтор |
   | `VALIDATION_FAILED` | нет | шлюз проверки не пропустил текст: ветка ремонта |
   | `DATA_INSUFFICIENT` | нет | нет данных за дату: деградация, а не отказ |
   | `CONFIG_ERROR` | нет | нет версии модели в реестре, нет промпта |
   | `INTERNAL` | нет | непойманное исключение |

   Различие `SOURCE_UNAVAILABLE` и `SOURCE_MALFORMED` принципиально: первое лечится повтором,
   второе повтором только тратит время и деньги. Платформа принимает в `errorList` воркфлоу только
   собственные коды (`STEP_TIMEOUT` и т.п.), поэтому класс функция возвращает в ответе, а решение о
   повторе принимает проверка ответа в самом воркфлоу.
5. **Обучение — вне облака.** Модель обучается локально или на виртуальной машине, в облако уезжает
   только JSON с деревьями и калибратором (формат `heliogeo.gbm.v1`), инференс зависит только от
   numpy. Порядок признаков проверяется при загрузке артефакта: разошедшийся порядок не вызывает
   исключения, а тихо портит прогноз. Выкладка модели — загрузка файла и обновление
   `registry/current.json`, откат — возврат указателя; передеплой функции не нужен.

### Лимиты, из которых следует архитектура

| Лимит | Значение | Следствие |
|---|---|---|
| Вход и выход шага воркфлоу | 2 МБ | шаги обмениваются ключами |
| Запрос и ответ функции | 3,5 МБ | то же |
| Время шага воркфлоу / запуска | 10 минут / 48 часов | бэкфилл дробится на месяцы, состояние копится в Object Storage |
| Переменные окружения функции | 4 КБ суммарно | конфигурация — в Object Storage, секреты — в Lockbox |
| `/tmp` функции | 512 МБ | хватает на суточный объём, не хватает на бэкфилл |
| Пакет функции | 3,5 МБ (консоль), 128 МБ (из S3, сжатый), 680 МБ (несжатый) | тяжёлые зависимости не помещаются |
| Установка зависимостей при сборке | 5 минут, 1 ГБ памяти | обучение в функцию не помещается |
| Функций в облаке / одновременных вызовов в зоне | 10 / 10 (квоты) | квоты поднимают заранее |

Значения сверены с документацией Yandex Cloud на 5 октября 2026; перед выкладкой их стоит
проверить ещё раз.

## Слои кода

| Слой | Модуль | Ответственность |
|------|--------|-----------------|
| Ядро | core/ | Config, logging |
| Контракт | schema/ | Pydantic-модели UnifiedPayload; схемы строк слоя L1 (`schema/l1.py`) |
| Извлечение | extractors/ | Клиент SWX API: типизированные ответы, приведение к моменту запроса, маппинг в payload (`extractors/swx`). Пакеты `influx`, `dav`, `blobs`, `solar`, `technical` — заготовки первоначального замысла, не используются |
| Оркестрация | pipeline/ | build_payload, run_pipeline (локальный сквозной прогон одним вызовом), классы ошибок шагов |
| LLM | llm/ | Providers, prompts, grounding |
| Продукты | products/ | ICAO, SWPC, simplified |
| Контракты | contracts/ (данные), heliogeo/contracts/ (код) | Версионируемые YAML под подписью эксперта: реестр фактов, словарь терминов, пороги, спецификации признаков |
| Хранилище | storage/ | Локальная PostgreSQL для разработки и тестов: подключение, ORM-модели (логическая схема, эталон для YDB); миграции — migrations/. Для облака: построители ключей Object Storage (`keys.py`) и интерфейс хранилища объектов с локальной реализацией (`objects.py`) |
| Сырьё | mirror/ | Ответы и файлы источника как получены; повторный запрос не идёт в сеть. Запись и манифест за дату — `mirror/raw.py` (пока для тел ответов `/data` и `/text`). В облаке — бакет `raw` |
| Факты | facts/ | Единственный источник значений: значение + происхождение + качество + политика отображения |
| Признаки | features/ | Признаки для прогнозных моделей строго на момент времени |
| Прогноз | forecast/ | Вероятностные прогнозы, базовые модели, калибровка |
| Планировщик | planner/ | Что сообщить в выпуске и в каком порядке |
| Генерация | generation/ | Текст выпуска по плану и фактам |
| Проверка | validation/ | Проверка сгенерированного текста относительно фактов |
| Публикация | publishing/ | Идемпотентная отправка по каналам, манифест выпуска |
| Оценка | eval/ | Эталонный набор текстов, метрики, сравнение версий |
| Рендер | render/ | TXT, PDF, HTML |
| Доставка | delivery/ | Telegram, email, web |
| CLI | cli/ | version, validate, run |
| Развёртывание | deploy/ | docker compose для локальной БД, спецификации воркфлоу (`deploy/workflows`) |

Пакеты `mirror/`, `features/`, `forecast/`, `planner/`, `generation/`, `validation/`,
`publishing/` и `eval/` — заготовки целевой структуры: пока в них только описание назначения, код
появляется по мере реализации. В `facts/` уже есть модель факта, правила отображения чисел и
сериализация — см. [Факты](facts.md).

## Границы модулей

Часть правил проверяется автоматически командой `lint-imports` (она входит в `make lint`);
настройки лежат в `pyproject.toml`, раздел `[tool.importlinter]`. Запрещены и косвенные
импорты: цепочка `a → b → c` нарушает запрет `a → c`.

| Модуль | Не может импортировать | Зачем |
|--------|------------------------|-------|
| generation | storage, extractors | Значения приходят только через факты, а не прямо из базы или источника |
| validation | llm.prompts | Проверка не знает, как составлен промпт генератора, и остаётся независимой |
| forecast | llm, generation | Прогноз не зависит от текста |

Практическое следствие: `heliogeo/llm/__init__.py` реэкспортирует промпты, поэтому из
`validation` нужно импортировать конкретные модули (например, `heliogeo.llm.base`), а не пакет
`heliogeo.llm` целиком. Новое правило добавляется в `pyproject.toml`; тест
`tests/unit/test_import_boundaries.py` проверяет, что каждое правило ловит нарушение.

## Поток данных

1. Extract — extractors читают источники и убирают то, чего на момент запроса ещё не было
   (см. [Data Sources](data_sources.md))
2. Build — pipeline/builder.py собирает UnifiedPayload
3. Generate — LLM генерирует текст из JSON + промпта
4. Grounding — проверка: все числа в тексте есть в JSON?
5. Render — конвертация в TXT/PDF
6. Deliver — отправка в Telegram / email / Web

Локально (`heliogeo run`) все шаги идут одним вызовом `run_pipeline`; в облаке тот же поток
разложен на функции и шаги воркфлоу (таблица выше). Момент данных задаётся параметром `--date`, и
в нём же — момент выпуска продукта: повторный прогон за ту же дату даёт тот же выпуск.

## Ключевые решения

| Решение | Альтернатива | Почему |
|---------|--------------|--------|
| Единый JSON | Сырые данные в LLM | Контракт, тестируемость |
| Pydantic | dict | Валидация, автодок |
| Grounding regex | LLM-проверка | Детерминизм |
| YAML | Python-константы | Менять без пересборки |
| Poetry | pip | Lock, группы |
| Оркестрация в Yandex Workflows | Планировщик внутри приложения | Нет долгоживущих процессов; ветвление, повторы и ограничения описаны декларативно, вся работа — в функциях |
| Шаги обмениваются ключами объектов | Передача данных между шагами | Лимит шага воркфлоу 2 МБ; на бэкфилле не проходит ничего |
| Время из события | `datetime.now()` в коде функций | Воспроизводимость: прогон за 2019 год не должен знать, что сейчас 2026-й |
| Класс ошибки в ответе функции | Разбор текста исключения | По классу решают, повторять ли шаг; повтор не лечит неразобранный файл |
| Обучение вне облака, в облако — JSON-артефакт | Обучение внутри функции | Сборка функции ограничена пятью минутами и 1 ГБ; в инференсе только numpy (43 МБ вместо ≈370 МБ); откат модели — смена указателя |

## Технологии

Python 3.11+, Pydantic 2.x, Typer 0.12, pytest 8.x, ruff 0.4, mypy strict. Локально: PostgreSQL 17
(docker compose), SQLAlchemy 2.x, Alembic, psycopg 3. Облако: Yandex Workflows (YaWL), Cloud
Functions (Python), Object Storage, YDB, Yandex Query, Lockbox.

## Ограничения

- LLM не имеет доступа к интернету — только JSON
- Grounding обязателен перед доставкой
- Enlil — анимация, численная интерпретация — TODO
- VLM для изображений — не используется
- Облачный контур описан спецификацией воркфлоу, но функции-обработчики, реализация хранилища объектов
  для Object Storage, обёртка YDB и перенос парсеров источника ещё не написаны; спецификация воркфлоу на стенде не
  запускалась
